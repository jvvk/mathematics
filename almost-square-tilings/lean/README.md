# Lean formalisation: Tiling almost-squares with smaller distinct almost-squares

Main theorems:

    theorem almost_square_tilings (n : ℕ) (hn : 1 ≤ n) :                       -- Final.lean, unit cells
        (∃ ts : List Tile, Admissible n ts) ↔ n ∈ [4, 10, 12, 14, 15, 18] ∨ 20 ≤ n
    theorem almost_square_tilings_real (n : ℕ) (hn : 1 ≤ n) :                  -- Real.lean, real rectangles
        (∃ ts : List RTile, RAdmissible n ts) ↔ n ∈ [4, 10, 12, 14, 15, 18] ∨ 20 ≤ n

Axioms: `propext`, `Classical.choice`, `Quot.sound`, plus, for the impossibility of n = 16, 17, 19
(No16/No17/No19), one auxiliary axiom per use of `native_decide`, such as
`AlmostSq.noTiling_16._native.native_decide.ax_1_1`, which asserts what the compiled search returned:
trust in Lean's compiler as well as its kernel (the kernel run needs more memory than a laptop has).
Everything else, including all existence data, is checked by the kernel. Those three cases are also
settled by two independent programs in the paper's ancillary files.

Mutation tests: `./mutants.sh` (28 mutants, each must be rejected; 11 unmutated baselines, each must pass).

The constructive direction follows the paper: each residue class is stored as its shift and threshold,
checked against the hypotheses of Lemma 4 at `t₀` (in 8 kernel pieces, peak ~4.4 GB), and its tilings
are produced by `inflation` and `all_scales`. `friedman_twenty` uses only `propext`, `Classical.choice`,
`Quot.sound`. Data: `Inflations.lean`, `Explicit.lean` and `Reach.lean` are generated by
`gen_lean.py` from `../verify/out` (rerunning it reproduces them; only the header comment of `Reach.lean` names the public paths).

Build: `lake exe cache get && lake build` (compiles everything and prints the axiom audit in `AlmostSquares/Audit.lean`). Peak memory about 4.4 GB.

Not formalised: the cited minimality facts (order 21, side 110; exhaustive enumerations in the
literature), the history, and statements about the software. The search node count is a property of a
program, not of the mathematics.
